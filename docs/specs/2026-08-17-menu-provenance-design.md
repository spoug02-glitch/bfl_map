# 메뉴 데이터 출처 전환

2026-08-17

## 왜

메뉴 20,560건이 전부 카카오의 비공식 endpoint(`place-api.map.kakao.com/places/panel3`) 한 곳에서 온다.
`collector/menu.py`는 그게 비공식임을 스스로 문서화하고 있다 — `pf: web` 헤더와 브라우저 UA를
위조해야 응답하고, 응답에 딸려오는 메뉴 사진은 **출처를 밝힐 수 없어서** 의도적으로 버린다.

이 의존을 걷어내고 싶다. 그런데 메뉴를 그냥 지우면 안 된다. 실측:

- 전체 5,834곳 중 메뉴 보유 **4,442곳** (편의점 제외 기준 **86.9%**)
- 메뉴 총 **20,560건** (가격 있음 15,307 / 미공개 `-1` 5,132 / 빈 문자열 121)

## 진짜 비용은 데이터가 아니라 가격 필터다

메뉴를 끄면 화면 여러 곳이 비지만, 대부분은 이미 검증된 경로다 — 메뉴 없는 1,392곳이
지금도 그렇게 동작한다. 무너지는 건 하나다: **가격 필터**.

`effectiveMinPrice`(`lib/constants.ts:84`)가 카카오 메뉴를 1차 입력으로 삼고, 사용자 제보를
보조로 얹는 구조다. 크롤러를 끄면 1차 입력이 사라져 필터의 후보가 제보 건수까지 떨어진다.

숨은 의존이 하나 더 있다. `lib/dislikes.ts:75-81`의 "안 먹는 음식" 필터가 **메뉴명 문자열**로
판정한다. 메뉴가 비면 이 필터는 에러 없이 조용히 무력화된다.

## 결정: 처분보다 이관을 먼저 한다

즉시 삭제(A)·기존 유지(B)·숨기고 교체(C)를 검토했다. 셋 다 "지금 무엇을 할 것인가"를 묻는데,
셋의 비용이 모두 **가격 필터가 카카오에 묶여 있다는 사실**에서 나온다. 그래서 순서를 뒤집는다.

1. `menu_items` 테이블을 만들고 **`effectiveMinPrice`가 DB를 먼저 보게** 한다. 카카오 메뉴는 fallback.
2. 제보 유입을 늘려 DB 커버리지를 쌓는다.
3. 커버리지가 충분해지면 그때 A/B/C를 고른다 — **그 시점에는 어느 쪽을 골라도 화면이 안 무너진다.**

이 순서의 대가는 명확하다: 그동안 카카오 유래 데이터가 계속 노출된다. 그 판단은 이 문서가
내리지 않는다. 이 문서가 보장하는 건 **언제 끄기로 하든 끌 수 있는 상태**를 만드는 것뿐이다.

## 저장 위치를 파일에서 DB로 옮긴다

지금 메뉴는 `web/public/restaurants.json`의 배열 필드다. 이 구조에는 두 가지가 불가능하다.

- **출처를 적을 자리가 없다.** 메뉴 항목 필드는 `{name, price}` 둘뿐이다.
- **부분 보존이 안 된다.** 수집기가 매 실행 파일을 통째로 다시 쓴다(`collect.py:262`).
  `--skip-menus`로 한 번 돌리는 순간 20,560건이 전부 사라진다.

식당 기본 정보는 파일에 그대로 둔다. 옮기는 건 메뉴뿐이다.

## 스키마

```sql
CREATE TABLE menu_items (
  id           SERIAL PRIMARY KEY,
  place_id     TEXT NOT NULL,
  menu_name    TEXT NOT NULL,
  price        INTEGER,
  source_type  TEXT NOT NULL CHECK (source_type IN
                 ('public_data','owner','user_report','official_source','legacy_import')),
  source_ref   TEXT,
  collected_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  verified_at  TIMESTAMPTZ,
  status       TEXT NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending','published','rejected'))
);
CREATE INDEX idx_menu_items_place ON menu_items (place_id, status);
```

### `verified_at` 은 "누가" 확인했는지를 가리지 않는다 (2026-08-17 정정)

초안은 이 칸을 "운영자/업주가 확인한 시각"으로 좁게 적었다. 그런데 공공데이터
임포터가 착한가격업소의 기준일을 여기 넣는다. 리뷰에서 "정의와 다르다"는 지적이
나왔고, 두 갈래가 있었다 — 공공데이터는 `verified_at`을 비우거나, 정의를 넓히거나.

**정의를 넓힌다.** 착한가격업소 지정은 지자체가 가격을 확인하는 절차 그 자체이고,
그건 우리 운영자의 확인보다 약한 근거가 아니다. 비워두면 화면에서 "언제 기준
값인지"를 잃는데, 그건 이 칸이 있는 이유를 없애는 선택이다.

그래서 `verified_at` = **확인 주체가 그 값을 확인한 시각**이다. 출처별로:

| source_type | verified_at |
|---|---|
| `public_data` | 데이터셋 기준일(착한가격업소는 분기 기준일) |
| `owner` | 업주가 등록·수정한 시각 |
| `user_report` | 교차검증으로 published 가 된 시각 |
| `official_source` | 그 출처가 밝힌 기준일 |
| `legacy_import` | 없음(NULL) — 확인 주체가 없다 |

화면은 이 값을 "YYYY. M. D. 확인"으로 쓴다. 누가 확인했는지는 옆의 출처 배지가 말한다.

`price`가 NULL 허용인 이유: 카카오가 미공개를 `-1`로 주는 걸 그대로 옮기면 `formatPrice`와
`cheapestMenu`가 각자 다시 걸러야 한다. 들어올 때 한 번 NULL로 정규화하고, 그 뒤로는
"가격 없음"이 타입으로 표현된다.

### `source_type` 명칭

요청받은 예시는 `public_api` / `owner` / `user_report` / `official_source` 였다. 둘을 바꾼다.

- **`public_api` → `public_data`**: 공공데이터는 API로만 오지 않는다. 파일 배포(CSV/XLSX)가
  흔하고, `_api`라는 이름은 그때 거짓말이 된다.
- **`legacy_import` 추가**: 기존 카카오 유래 데이터를 DB로 옮길 경우 다른 출처와 섞이면
  안 된다. 이 값이 없으면 "숨기고 순차 교체"라는 선택지 자체가 구현 불가능해진다.

### `status`

제보 한 건이 곧바로 확정 데이터가 되지 않게 한다.

- `pending` — 기본값. 화면에 약하게 표시된다.
- `published` — 서로 다른 사용자 2명이 ±20% 안의 가격을 냈을 때. 담합 비용이 계정 2개다.
- `rejected` — 운영자가 내린 것.

3단계(어드민 검토 큐)는 이 문서의 범위 밖이다. `/admin`과 정지 기능이 이미 있어 나중에 붙일
자리는 있다. **1~2단계만으로 "한 사람이 혼자 가격을 확정할 수 없다"가 성립한다.**

## 제보 UI는 새로 만들지 않는다

`SpecialSection`이 이미 이 일을 한다. `PlacePanel`의 메뉴 목록 바로 아래에 있고, 메뉴가 없는
가게에서도 렌더된다. 검증도 이미 있다 — 메뉴명 40자, 가격 500~100,000원, 1분 5건 rate limit,
`PK(place_id, user_id)` upsert로 한 사람당 한 가게 하나.

바꾸는 건 진입 문구뿐이다.

| 상황 | 문구 |
|---|---|
| 메뉴 있음 | "점심 특선 제보받아요" (현행) |
| 메뉴 없음 | "이 집 메뉴를 아시나요?" / "드셔보신 메뉴와 가격을 알려주세요." |

입력은 **메뉴명 + 가격** 둘로 충분하다. 별점·비고는 이미 선택 입력이다.

## 같이 고치는 것 — 스키마 드리프트

`web/schema.sql`에 `lunch_specials`, `saved_places`, `withdrawals` 세 테이블이 없다.
마이그레이션에만 있다. 이 저장소가 전에 두 번 겪은 문제고, 새 DB를 만들면 이 테이블들이
조용히 사라진다. 메뉴 작업과 무관한 기존 결함이지만 `schema.sql`을 어차피 건드리므로 같이 고친다.

## 하지 않는 것

- **크롤러를 지금 끄지 않는다.** 3단계에서 결정한다.
- **기존 데이터를 지금 처분하지 않는다.** 같은 이유.
- **메뉴 사진은 앞으로도 수집하지 않는다.** `menu.py`의 기존 방침을 유지한다.
- **어드민 검토 큐는 만들지 않는다.** 2단계 교차검증으로 충분하다.
- **`restaurants.json`의 식당 기본 정보 구조는 건드리지 않는다.**

## 알려진 한계

- 2단계 교차검증은 **가격이 실제로 맞는지**를 보증하지 않는다. 두 사람이 같은 오해를 할 수 있다.
  보증하는 건 "한 계정이 혼자 확정할 수 없다"뿐이다.
- 커버리지 임계값을 아직 못 정했다. `lunch_specials`의 현재 행 수를 이 워크트리에서 확인할 수
  없기 때문이다(`.env.local` 없음). 3단계에 들어가기 전에 실측해야 한다.
- 재사용 가능한 공공 메뉴 데이터가 실제로 존재하는지 확인되지 않았다. `public_data` 출처는
  자리만 만들어 두는 것이고, 채울 수 있을지는 별도 조사가 필요하다.
