# 서비스 전용 표시 닉네임

작성일: 2026-08-04

## 문제

로그인하면 헤더와 리뷰에 카카오/구글 프로필 이름이 그대로 뜬다. 대부분의 사람은
카카오 프로필에 본명을 쓰기 때문에, 회사 근처 점심 리뷰에 실명이 붙는다. 직장인이
쓰는 앱에서 이건 리뷰를 안 쓰게 만드는 이유가 된다.

카카오맵처럼 서비스 안에서만 쓰는 표시 이름을 갖게 한다.

## 결정 사항

1. **첫 로그인 시 닉네임을 정하게 한다.** 본명이 화면에 단 한 번도 뜨지 않는다.
2. **닉네임을 바꾸면 과거 리뷰의 이름도 같이 바뀐다.** 표시 이름의 출처는 한 곳뿐이다.
3. **프로바이더가 준 이름은 어디에도 저장하지 않는다.** 콜백에서 받는 즉시 버린다.

## 온보딩 방식

홈 화면 모달로 한다. `/api/auth/me`가 닉네임 미설정을 알려주면 홈에서 닫을 수 없는
모달을 띄운다.

별도 `/onboarding` 페이지를 만드는 대안도 있었다. 우회가 불가능하다는 장점이 있지만
라우트 추가에 더해 뒤로가기와 직접 접근 분기를 전부 처리해야 한다. 이 앱은 사실상
단일 페이지이고 로그인은 리뷰를 쓸 때만 하므로, 지도를 배경에 둔 채 뜨는 모달이
흐름을 덜 끊는다. 서버 측 409 가드(아래)가 우회 경로를 막으므로 모달이 유일한
방어선도 아니다.

## 데이터 모델

```sql
CREATE TABLE IF NOT EXISTS users (
  user_id    TEXT PRIMARY KEY,   -- namespacedUserId(): 'kakao:123' / 'google:abc'
  nickname   TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`reviews.nickname`은 제거하고 조회할 때 `users`를 조인한다. 이게 결정 2를 구조로
보장한다 — 이름이 한 곳에만 있으면 과거 리뷰가 어긋날 수가 없다.

### 마이그레이션 순서

기존 리뷰의 이름을 잃지 않도록 백필을 먼저 한다. 마이그레이션을 먼저 돌리고 그다음
배포한다.

```sql
INSERT INTO users (user_id, nickname)
  SELECT DISTINCT ON (user_id) user_id, nickname
  FROM reviews
  ORDER BY user_id, updated_at DESC
  ON CONFLICT (user_id) DO NOTHING;

ALTER TABLE reviews
  ADD CONSTRAINT reviews_user_fk FOREIGN KEY (user_id) REFERENCES users (user_id);

ALTER TABLE reviews DROP COLUMN nickname;
```

외래 키를 거는 이유는 "users 행 없는 리뷰"라는 상태를 아예 만들 수 없게 하기
위해서다. 그래야 조회 쿼리가 `INNER JOIN`으로 끝나고, 이름이 빈 리뷰를 화면에서
처리할 일이 없다.

## 세션 흐름

세션 JWT는 `sub`(userId)만 싣는다. 표시 이름은 항상 DB에서 읽는다.

현재는 프로바이더가 준 이름이 JWT의 `nickname` 클레임에 실려 있고, 그래서 본명이
뜬다. 이 클레임을 없앤다. `verifySessionToken`은 `sub`만 요구하도록 완화한다 —
이미 발급된 세션에는 `nickname`이 남아 있는데, 그 값을 무시하고 통과시키면 기존
로그인 사용자를 강제로 로그아웃시키지 않아도 된다.

`GET /api/auth/me` 응답:

| 상태 | 응답 |
|---|---|
| 비로그인 | `{ "user": null }` |
| 로그인 · 닉네임 있음 | `{ "user": { "userId": "...", "nickname": "점심러4821" } }` |
| 로그인 · 닉네임 없음 | `{ "user": { "userId": "...", "nickname": null } }` |

`nickname`이 `null`이면 프론트가 온보딩 모달을 띄운다.

## 닉네임 규칙

- **2~12자.** 코드 포인트로 센다(`[...s].length`) — 한글 한 글자가 1로 세어져야 한다.
- **한글·영문·숫자·밑줄만.** `/^[가-힣a-zA-Z0-9_]+$/`. 공백과 특수문자는 막는다.
  자모 단독(`ㄱ`, `ㅏ`)은 `가-힣` 범위 밖이라 자연히 걸러진다.
- **리뷰 본문과 같은 욕설 필터**(`containsProfanity`)를 적용한다.
- **중복을 허용한다.** 유니크 제약은 "이미 사용 중입니다" 마찰만 크고, 리뷰의 소유권
  판별은 `user_id`로 하므로 이름이 겹쳐도 기능상 문제가 없다.
- **변경 횟수 제한 없다.** 헤더의 닉네임을 누르면 같은 모달이 변경 모드로 열린다.

### 자동 제안값

첫 모달의 입력칸에 `점심러` + 4자리 숫자(1000–9999)를 미리 채운다. 그대로 [확인]만
눌러도 통과하므로 이름 짓기가 부담인 사람도 막히지 않는다. 중복을 허용하므로 충돌을
검사하지 않는다.

프로바이더 이름을 제안값으로 쓰지 않는다. 본인에게만 보이는 값이긴 하지만, 그걸
그대로 확정하면 결국 본명이 노출된다.

## API

`PUT /api/auth/nickname` 하나가 최초 설정과 변경을 겸한다.

- 요청: `{ "nickname": "점심러4821" }`
- 세션 없음 → `401 { "error": "로그인이 필요합니다." }`
- 검증 실패 → `400 { "error": "<한국어 사유>" }`
- 성공 → `200 { "nickname": "점심러4821" }`, `users`에 upsert

에러 응답 모양은 기존 리뷰 API와 같게 맞춘다.

`POST /api/reviews`에 가드를 하나 추가한다. 닉네임이 없는 세션이 리뷰를 쓰려 하면
`409 { "error": "닉네임을 먼저 설정해주세요." }`로 막는다. 모달을 우회해 API를 직접
호출한 경우에 대한 방어다.
