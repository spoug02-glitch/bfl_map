# 업주 등록 · 제보 접수

2026-08-18

## 왜 지금 뒤집는가

`app/(docs)/contact/page.tsx` 에는 이런 주석이 있다.

> 별도 고객센터를 두지 않는다. 혼자 운영하는 서비스에서 접수 시스템을 만들어두면
> 답이 늦을 때 오히려 방치된 창구가 된다.

그 판단은 지금도 절반은 맞다. 바뀐 건 **어드민이 생겼다는 것**이다. 그때는 접수한
글이 어디에도 쌓이지 않아 메일함에서만 살았지만, 지금은 `/admin` 에 검토 큐를 둘 수
있고 운영자 계정·정지 기능도 이미 있다. "방치된 창구"의 원인이 사라졌으므로 연다.

그리고 지금은 받아야 할 게 훨씬 많아졌다. 카카오 메뉴를 걷어낸 뒤 가격 필터가
5,109곳 중 51곳에서만 동작한다. 메뉴를 **받을 경로**가 서비스의 병목이다.

## 업주 메뉴는 새 테이블을 만들지 않는다

`menu_items` 가 이미 이 일을 하도록 설계돼 있다.

- `source_type = 'owner'` — 다섯 출처 중 하나로 이미 있다
- `status = 'pending'` — 기본값이고, 확정 전에는 가격 필터가 세지 않는다(`dbMinPrice`)
- `verified_at` — 승인 시각을 적는 자리가 있다

업주 제출은 **pending 행 삽입**, 어드민 승인은 **published 전환**이다. 그 이상 필요 없다.

자유서술 제보는 모양이 달라서(가게가 없을 수도, 여러 문장일 수도) 별도 표를 둔다.

## 검증: 어드민 승인

아무나 "내 가게다"라고 할 수 있다는 게 문제다. 세 가지를 검토했다.

- **전화번호 인증** — `restaurants.json` 에 가게 전화번호가 이미 있어 근거는 가장 강하다.
  SMS 발송 연동과 비용이 필요해 지금 규모에는 과하다.
- **바로 노출** — 경쟁 가게가 남의 가격을 조작할 수 있다. 안 된다.
- **어드민 승인** ← 채택. 대상이 수십 곳이라 손으로 감당된다. 추가 비용 0.

승인 전까지 업주 메뉴는 화면에 "미확인"으로 뜨고 가격 필터에는 안 들어간다. 이 동작은
이미 구현돼 있다.

## 로그인은 요구하지 않는다

제보와 업주 등록 둘 다 비로그인으로 받는다. 카카오 로그인을 요구하면 가게 주인도,
"여기 폐업했어요"를 알려주려던 사람도 그 자리에서 떠난다. 접수 경로를 만드는 이유가
문턱을 낮추는 것인데 문턱을 세우면 앞뒤가 안 맞는다.

대신 **아무것도 자동으로 반영되지 않는다.** 스팸이 들어와도 어드민 받은함이 지저분해질
뿐 데이터는 오염되지 않는다. 그래서 스팸 대책은 최소로 둔다 — 길이 상한, 분당 제출 수
제한, 그리고 봇이 채우면 버리는 허니팟 한 칸.

## 스키마

```sql
CREATE TABLE reports (
  id          SERIAL PRIMARY KEY,
  kind        TEXT NOT NULL CHECK (kind IN
                ('place_fix','delist','abuse','feature')),
  place_id    TEXT,
  body        TEXT NOT NULL CHECK (length(trim(body)) > 0),
  contact     TEXT,
  status      TEXT NOT NULL DEFAULT 'open'
                CHECK (status IN ('open','handled','rejected')),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  handled_at  TIMESTAMPTZ,
  handled_by  INTEGER REFERENCES admin_users (id)
);
CREATE INDEX idx_reports_open ON reports (created_at DESC) WHERE status = 'open';
```

네 종류는 `/contact` 가 이메일로 받던 목록에서 그대로 왔다.

| kind | 화면 문구 |
|---|---|
| `place_fix` | 가게 정보가 달라요 (폐업·이전·가격) |
| `delist` | 가게 노출을 원하지 않아요 |
| `abuse` | 부적절한 리뷰·제보 신고 |
| `feature` | 기능 제안·불편 |

`contact` 는 선택이다. 답이 필요 없는 제보가 많고, 강제하면 그것 때문에 안 보낸다.
`place_id` 도 선택이다 — 가게와 무관한 제보가 있고, 가게 이름을 본문에 적는 사람도 있다.

부분 인덱스를 `status='open'` 에 거는 이유는 어드민이 보는 것이 사실상 열린 건뿐이기
때문이다. 처리된 건은 쌓이기만 하고 조회되지 않는다.

## 화면

- **`/owner`** — 가게를 고르고 메뉴명·가격을 여러 줄 넣는다. 연락처는 필수다(승인 전에
  확인할 일이 생긴다). 제출하면 `menu_items` 에 pending 으로 들어간다.
- **`/report`** — 종류를 고르고 본문을 쓴다. 가게는 선택.
- **`/contact`** — 이메일 안내를 두 페이지 링크로 바꾼다. 메일 주소는 남긴다. 두 갈래에
  안 맞는 일이 늘 있고, 그때 창구가 없으면 더 나쁘다.
- **`/admin/reports`** — 열린 제보와 pending 업주 메뉴를 한 화면에서 처리한다.

## 하지 않는 것

- **전화번호 인증** — 규모가 커지면 그때.
- **업주 계정** — 로그인·비밀번호·내 가게 관리 같은 건 만들지 않는다. 한 번 제출하고
  끝나는 흐름이다.
- **자동 이메일 회신** — 발송 연동이 없다. 답은 어드민이 연락처로 직접 한다.
- **제보 수정·삭제** — 보낸 사람이 다시 손댈 방법을 두지 않는다. 잘못 보냈으면 다시 보낸다.

## 알려진 한계

- 승인이 밀리면 업주 메뉴가 계속 "미확인"으로 남는다. 어드민이 보지 않으면 예전 주석이
  걱정하던 "방치된 창구"가 그대로 재현된다. 대시보드에 열린 건수를 띄워 그걸 막는다.
- 비로그인이라 같은 사람이 반복 제출하는 걸 계정으로는 못 막는다. 분당 제한만 있다.
- `delist` 는 접수만 한다. 실제로 가게를 빼는 건 `restaurants.json` 을 손봐야 하는
  별도 작업이고, 수집을 다시 돌리면 되살아난다. 그 구조는 이 문서 밖이다.
