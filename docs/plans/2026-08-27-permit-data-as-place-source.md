# 가게 목록 출처를 인허가 데이터로 전환 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 가게 목록의 출처를 제로페이 가맹점 명부에서 **행정안전부 인허가 데이터**로 바꾼다. 제로페이는 목록의 전제가 아니라 **필터 플래그**로 내린다.

**왜:** 제로페이 가맹점 지도는 차별점이 아니다 — 운영기관인 한국간편결제진흥원이 「제로페이 맵」(2024)을 직접 낸다. 결제까지 되고 전국이다. 우리가 가질 수 있는 자리는 "제로페이 되는 집"이 아니라 **"점심을 정해주는, 우리 동네, 메뉴·가격이 있는 지도"**다. 그러려면 제로페이 제약이 목록을 반으로 깎는 구조부터 풀어야 한다.

**부수 효과 — 카카오 매칭 손실이 사라진다.** 지금은 제로페이 7,467곳을 긁어 5,826곳만 들어온다. 1,469곳이 카카오에서 같은 가게를 못 찾아 좌표가 없어 탈락한다(전체의 약 1/5). **인허가 데이터는 좌표를 자체 제공**하므로 이 손실이 원리적으로 없어진다.

**Spec:** 없음. 아래 「먼저 결정할 것」의 ID 체계는 **구현 전에 별도 설계 문서가 필요하다.**

## Global Constraints

- **`kakao_place_id` 를 함부로 버리지 않는다.** `saved_places`·`reviews`·`menu_items`·`reports` 가 **전부 `kakao_place_id` 로만 조인한다**. 키를 바꾸면 기존 리뷰·저장·메뉴가 고아가 된다. 이 계획에서 제일 위험한 지점이다
- **`collector/zeropay.py` 를 지우지 않는다.** **역할만 바뀐다** — 목록 생성기 → 플래그 판정기.
  (`verify_zeropay.py` 는 2026-08-27에 지웠다 — 아래 Phase 4 절)
- **플랫폼을 긁지 않는다.** [[안 하는 것들]] 의 원칙 그대로. 인허가 데이터를 쓰는 이유의 절반이 이것이다
- **수집기는 `restaurants.json` 을 통째로 재작성한다.** 돌리기 전에 커밋돼 있어야 한다. `--limit` 스모크 테스트조차 파일을 덮는다
- **영업중만 넣는다.** 인허가 데이터의 영업상태로 거른다
- 검증 명령은 이 워크트리에 `.env.local` 이 없어 더미 env 가 필요하다:
  `DATABASE_URL="postgres://u:p@localhost:5432/db" ADMIN_SESSION_SECRET="x" SESSION_SECRET="x" npm run build`
  그리고 **dev 서버를 끈 상태에서 `npx vitest run`**

## Phase 0 실측 결과 — 2026-08-27 (완료)

### API 명세 확정

```
http://apis.data.go.kr/1741000/general_restaurants/info    # 일반음식점
http://apis.data.go.kr/1741000/rest_cafes/info             # 휴게음식점
http://apis.data.go.kr/1741000/tourist_restaurants/info    # 관광식당
```

파라미터: `serviceKey`, `pageNo`, `numOfRows`(**최대 100**), `resultType=json`,
그리고 조건은 **`cond[필드::연산자]=값`** 문법이다.

```
cond[OPN_ATMY_GRP_CD::EQ]=3090000   # 도봉구
cond[SALS_STTS_CD::EQ]=01           # 영업/정상
cond[DAT_UPDT_PNT::GTE]=20260301000000   # 변동분만
```

> **`localCode` 는 이 API에 없다.** 넘겨도 조용히 무시되고 전국 결과가 온다.
> 실제 지역 필드는 **`OPN_ATMY_GRP_CD`** 다. 이걸 모르고 짜면 제주 데이터를 받는다.

자치단체코드: **도봉 `3090000` · 노원 `3100000` · 강북 `3080000`**

주요 응답 필드: `MNG_NO`(관리번호) · `BPLC_NM`(사업장명) · `BZSTAT_SE_NM`(업태구분명) ·
`SALS_STTS_CD/NM` · `DTL_SALS_STTS_NM` · `ROAD_NM_ADDR` · `LOTNO_ADDR` ·
**`CRD_INFO_X`/`CRD_INFO_Y`**(EPSG:5174) · `TELNO` · `LCPMT_YMD` · `CLSBIZ_YMD` ·
`FCLT_TOTAL_SCL` · `DAT_UPDT_PNT`

## ID 체계 — **A안으로 결정** (2026-08-27)

원래 이 절은 "구현 전 별도 설계가 필요한, 되돌리기 비싼 결정"이었다.
**Phase 0 이 그 전제를 없앴다.**

> [!warning] 2026-08-27에 뒤집힘 — C안 권고를 철회한다
> 원래 **C안**(인허가를 기본키로, `kakao_place_id` 는 별칭 컬럼으로 병기)을 권했다.
> 근거는 *"기존 리뷰·저장이 고아가 된다"* 였는데, **실측하니 리뷰 2건 저장 0건이다.**
> 지킬 것이 없는데 매핑 테이블과 이행기 코드를 떠안을 이유가 없다.

**A안: 인허가 `MNG_NO` 를 기본키로 삼는다.**

- 좌표·영업상태가 원본과 1:1
- **카카오 매칭 의존이 끝난다** — 1/5 손실의 원인이 사라진다
- 옮길 것: `menu_items` 184행(53곳)뿐. 53곳이면 스크립트가 실패해도 손으로 끝난다
- `reviews` 2건 · `lunch_specials` 2건 · `reports` 1건은 손으로 옮긴다

> [!note] `kakao_place_id` 를 완전히 버리지는 않는다
> 카카오 지도 SDK 와 공유 링크가 그걸 쓴다. **선택 필드로 남기되, 조인 키에서만 뺀다.**

## ~~먼저 결정할 것 — ID 체계 (구현 전 설계 필요)~~ — 위에서 결정됨

**이 계획에서 유일하게 되돌리기 비싼 결정이었다.**

지금 구조: `restaurants.json` 에 있다 = 제로페이 가맹점이고, 모든 사용자 데이터가 `kakao_place_id` 로 그 행을 가리킨다. 인허가 데이터로 넘어가면 **가게의 신원을 무엇으로 삼을지**를 새로 정해야 한다.

| 안 | 내용 | 값 | 대가 |
|---|---|---|---|
| A | 인허가 `관리번호` 를 새 기본키로 | 좌표·상태가 원본과 1:1, 카카오 의존 종료 | **기존 리뷰·저장·메뉴 전부 재매핑 필요** |
| B | `kakao_place_id` 유지, 인허가는 보강용 | 사용자 데이터 무손상 | 카카오 매칭 실패 1/5 손실이 그대로 남는다 — 전환의 이유 절반이 사라짐 |
| C | 인허가를 기본키로, `kakao_place_id` 는 **별칭 컬럼**으로 병기 | 무손상 + 손실 해소 | 매핑 테이블과 이행기 코드가 늘어난다 |

**C 를 권한다.** 다만 매핑 정확도가 관건이고, 그건 [[데이터]] 가 이미 겪은 상호·주소 정규화 지옥과 같은 문제다 — `brands.py`·`kakao_local.py` 의 기존 정규화를 재사용할 수 있다.

**A 를 고르면 기존 리뷰가 날아간다.** 리뷰 수가 아직 적다면 감수할 수도 있다. **먼저 세어볼 것.**

## 관광식당 축 — 세보기 전에는 짓지 않는다

**아이디어:** 접대·손님 대접 상황. 할랄이나 특정 국가 음식을 찾는 검색은 답이 부실하다.
관광식당업은 관광진흥법상 **외국인 손님 접대를 전제로 지정**되는 업종이라 이 수요와 결이 맞고,
API도 이미 승인받았다.

**의심하는 이유:** 이 축은 지금까지 세운 것과 세 군데서 어긋난다.

- **점심이 아니다.** 접대는 저녁이고 가격대가 다르다. 여정 4단계 구조가 그대로 안 맞는다
- **지역이 안 맞을 가능성이 크다.** 할랄·외국인 접대 수요는 이태원·안산 쪽이지
  도봉·노원·강북이 아니다
- **축을 또 늘린다.** 메뉴 커버리지가 1%인 상태에서 새 축을 여는 건 순서가 틀렸다

**그래서 짓지 말고 셌다. 2026-08-27 실측: 도봉 0곳 · 노원 2곳 · 강북 0곳 — 3구에 2곳이다.**

미리 박아둔 기준표대로 **0~5곳이면 접는다.** 지도에 얹을 것이 없다.
**이 축은 종결한다** — 다시 꺼낼 거면 지역을 바꾸는 이야기부터 해야 한다.

| 3구 관광식당 수 | 판단 | |
|---|---|---|
| **0~5곳** | **접는다** | ← **실측 2곳** |
| 10~30곳 | 배지 하나로 표시 | |
| 50곳 이상 | 예상이 틀린 것 | |

> [!note] 할랄은 관광식당과 다른 데이터다
> 할랄 인증·무슬림 친화 식당은 한국관광공사가 따로 분류한다(인증/자가인증/프렌들리/포크프리).
> **관광식당 = 할랄이 아니다.** 관광식당 수가 0에 가까우면 할랄은 볼 것도 없고,
> 의미 있는 수가 나오면 그때 별도 출처를 찾는다. **확인 안 했다.**

## 하지 않는 것

- **메뉴·가격은 이 계획에 없다.** 인허가 데이터에 가격이 없다. 그건 걸어서 채운다 —
  창동역 300m 123곳부터. 별도 계획으로 분리한다
- **3구 밖으로 넓히지 않는다.** MVP 범위 그대로
- **든든한 점심밥 표시는 아직 안 한다.** 인허가 업태로 판정할 수 있어 보이지만
  시행지침의 제외 업종을 확인 안 했다. 확인 전에 표시하면 서울사랑상품권과 같은 실수가 된다
- **카카오 Local API 를 끊지 않는다.** C안이면 별칭 매칭에 계속 쓴다

## 감수하는 것

- **폐업 반영 지연.** 인허가는 "결제가 일어난다"는 신호가 없어서 제로페이보다 낡을 수 있다.
  대신 매일 갱신되고 영업상태 필드가 있다
- **가게 수가 2배 이상으로 뛰면 메뉴 커버리지 비율은 더 나빠진다.** 5,103 중 53곳이
  1만 중 53곳이 된다. **비율은 무의미해지고 거점별 밀도가 지표가 된다** — 그게 맞는 방향이다
